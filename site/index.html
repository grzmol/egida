Egida

Egida to lokalne proxy zgodne z API OpenAI. Proxy sprawdza ruch między agentem a modelem. Proxy przepuszcza (allow), maskuje (redact) albo blokuje (block) ruch według jednej polityki. Politykę zmieniasz na żywo. Proxy pilnuje budżetu każdego agenta i zapisuje dziennik audytu z łańcuchem hashy.

Przegląd

Problem, wymagania zadania i uruchomienie projektu.

O projekcie

Agenci AI w firmie wysyłają do modeli dane osobowe i sekrety. Agenci wykonują polecenia wstrzyknięte w dokumenty i wchodzą w pętle. Egida działa między agentem a modelem. Proxy wykrywa te zdarzenia i zatrzymuje je według jednej polityki.

Wymagania zadania i nasza odpowiedź

#Wymaganie (Goldman Sachs)RozwiązanieStan
R1Centralny silnik polityk: kontrole, progi, modele, budżetyJeden plik YAML ze schematem, przeładowanie na żywo bez restartu → Politykadziała
R2Kontrole deterministyczne i semantycznePII, sekrety, heurystyki injection + klasyfikator Prompt Guard 2 → Kontroledziała
R3Budżety: tokeny, czas, dostępTokeny, koszt i liczba żądań per agent, wykrywanie pętli, limity wejścia → Budżetydziała
R4Znane ataki: wykonanie kodu, deserializacja, łańcuch dostawFeed sygnatur z przeładowaniem na żywo (pickle, LangChain, Java, reverse shell, curl | sh, rm -rf /, Probllama, tool poisoning), allowlista modeli i ścieżek → Sygnaturydziała
R5Metryki dla zarządu, logi dla bezpieczeństwaDashboard, /api/stats, dziennik audytu z łańcuchem hashy, eksport → Audytdziała
R6Automatyczne testy, przypadki pozytywne i negatywnePrzypadki testowe w YAML: offline w CI i na działającej instancji → Testydziała

Różnice względem innych rozwiązań

  • Lokalnie i w open source. Klasyfikator działa w procesie proxy, bez chmury. LiteLLM, Kong i Portkey wysyłają kontrole semantyczne do płatnych usług albo dają je tylko w wersji Enterprise.
  • Jedna polityka, zmiana na żywo. Proxy odrzuca złą wersję i podaje powód. Ruch chroni ostatnia poprawna wersja.
  • Każda decyzja ma paragon: kontrola, wynik, hash polityki, tagi OWASP, czasy etapów.
  • Polski na równi z angielskim: PESEL, NIP, IBAN z sumami kontrolnymi; polskie frazy injection.
  • Jury samo uruchamia testy na działającej instancji.

Dwa oficjalne dokumenty podają różne wagi. Przyjmujemy wyższą wagę testów. Jury uruchamia nasze testy, wpisuje własne prompty i zmienia politykę na żywo.

Proxy używa API OpenAI. Możesz uruchomić je za LiteLLM, Kongiem albo agentgateway. Proxy uzupełnia routing i nie zastępuje go.

Szybki start

Uruchom proxy trzema poleceniami. Aby podłączyć agenta, zmień tylko base_url.

uv sync
make run          # proxy na http://127.0.0.1:8080, polityka: config/policy.yaml
make models       # opcjonalnie: Prompt Guard 2 (ONNX), potrzebny tylko gdy prompt_guard jest włączony

Wymagania: macOS albo Linux, uv. Dla prawdziwych odpowiedzi modelu zainstaluj Ollamę i wykonaj ollama pull llama3.2:3b. Bez Ollamy blokady działają, a przepuszczone żądania dostają 502.

Python (SDK OpenAI)

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8080/v1",
                api_key="sk-demo-agent")
r = client.chat.completions.with_raw_response.create(
    model="llama3.2:3b",
    messages=[{"role": "user",
               "content": "My PESEL is 44051401359"}])
print(r.headers["x-egida-decision"])  # redact

curl

curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H 'Authorization: Bearer sk-demo-agent' \
  -d '{"model":"llama3.2:3b","messages":[
       {"role":"user",
        "content":"Ignore all previous instructions"}]}'
# HTTP 200, finish_reason "content_filter",
# X-Egida-Decision: block

Przepływ żądania

Etapy mają stałą kolejność: najtańsze są pierwsze. Każde żądanie używa jednej migawki polityki od początku do końca. Pierwsza blokada kończy pipeline. Proxy nie wywołuje wtedy modelu i zwalnia rezerwację budżetu.

  1. HTTPhttp_api.pysha256 klucza → agent (401), walidacja (400), allowlista ścieżek (404); żądanie → Interaction ze wszystkimi wiadomościami i narzędziami
  2. LimityC17 · limitza długie wejście albo za dużo wiadomości; proxy przycina żądane max_tokens do limitumoże blokować
  3. Dostęp do modeluC02 · access.modelmodel spoza allowed_models agentamoże blokować
  4. Rezerwacja budżetuC15/C16 · budget.*szacunek tokenów i kosztu przed wywołaniem; tokeny, koszt, liczba żądań, pętlamoże blokować
  5. Kontrole wejściadetektory, kolejność z politykikażda kontrola ma własny timeout; proxy łączy maskowania z wielu detektorów i stosuje je, zanim tekst trafi do modelumoże blokować
  6. ModelModelClientupstream z polityki; błąd sieci lub HTTP → 502 i upstream_error
  7. Kontrole wyjściate same detektory, strona wyjścianp. PESEL albo klucz w odpowiedzi modelumoże blokować
  8. RozliczenieBudgetStore.settleproxy zamienia rezerwację na rzeczywiste usage
  9. Agregacja i audytAuditSinknajsilniejsza akcja wygrywa; jedno zdarzenie decision z wynikami, budżetem i czasami etapów

Czasy etapów w dzienniku audytu: limits, access, budget, input:<kontrola>, redact_input, model, output:<kontrola>, total. Z nich dashboard liczy p50 i p95.

Streaming

Przy stream: true tokeny wysyłane na bieżąco ominęłyby kontrole wyjścia. Proxy pobiera całą odpowiedź i sprawdza ją. Potem proxy odtwarza odpowiedź jako SSE zakończone [DONE]. Klient działa bez zmian. Nie ma tylko strumieniowania token po tokenie.

Jak zapada decyzja

Decyzja ma trzy możliwe wyniki: ALLOW REDACT BLOCK. Najsilniejszy wynik wygrywa. Każdy błąd kontroli domyślnie blokuje (fail-closed).

Odpowiedź blokująca

Blokada to HTTP 200 z poprawnym chat.completion, finish_reason: "content_filter", nagłówkami X-Egida-* i polem egida (paragon).

KodKiedy
200każda decyzja: allow, redact, block
401brak klucza API albo nieznany klucz API
400niepoprawne wejście
404ścieżka spoza allowlisty
502upstream jest niedostępny albo zwrócił błąd
Dlaczego 200, a nie 403 czy 429

Garak, promptfoo i SDK liczą kody błędów jako awarię, nie jako skuteczną obronę. Agent nie dostaje wtedy czytelnej odpowiedzi. SDK OpenAI samo ponawia 429. Odmowa budżetu jako 429 dałaby pętlę, którą budżet ma zatrzymać. Dostawcy modeli też używają finish_reason: "content_filter".

Konfiguracja i kontrole

Polityka, kontrole, budżety i dziennik audytu.

Polityka

Jeden plik YAML (config/policy.yaml) steruje kontrolami, progami, akcjami, modelami, agentami i budżetami. Zmiana działa w ok. 1 s bez restartu. Proxy odrzuca złą zmianę, a ruch chroni ostatnia poprawna wersja. Zmień politykę w konsoli Egidy (egd) albo w dowolnym edytorze.

Schemat v1

Schemat to Pydantic v2 w core/policy.py z extra="forbid". Literówka w nazwie pola odrzuca całą politykę. Proxy nie ignoruje takiego pola. Proxy sprawdza parametry każdego detektora przy ładowaniu polityki.

Zmiana polityki na żywo

  1. PolicyFile co 1 s liczy sha256 pliku. Polling działa tak samo na macOS, Linuksie i w Dockerze. Polling działa także wtedy, gdy edytor podmienia plik przy zapisie.
  2. Jeśli hash jest nowy, proxy wykonuje yaml.safe_load i sprawdza schemat oraz parametry detektorów.
  3. Jeśli polityka jest poprawna, proxy atomowo podmienia niezmienną migawkę i zapisuje zdarzenie policy_reloaded z diffem.
  4. Jeśli polityka jest niepoprawna, proxy zapisuje zdarzenie policy_rejected z powodem. GET /api/policy pokazuje last_error. Dashboard pokazuje czerwony baner „Policy change REJECTED”. Ruch dalej chroni ostatnia poprawna polityka.
  5. Możesz usunąć albo wyłączyć kontrolę. Dashboard pokazuje wtedy żółty baner „Posture weakened”.

Żądanie bierze migawkę na starcie. Przeładowanie w trakcie żądania nie zmienia tego żądania. X-Policy-Sha256 pokazuje wersję pliku, która dała decyzję.

Konsola Egidy

Konsola Egidy (egd) to narzędzie terminalowe w stylu wizualnym pi. Konsola zmienia całą politykę i profil uruchomienia, uruchamia i zatrzymuje proxy oraz pokazuje jego stan. Przed zapisem konsola sprawdza każdą zmianę walidacją proxy i pokazuje diff. Konsola działa poza ścieżką żądania i nie łączy się z agentami ani z modelami. Decyzja: ADR-0007.

egd                           # interfejs interaktywny (wymaga terminala); make egd = uv run egd
egd run                       # proxy na pierwszym planie z profilu uruchomienia, bez interfejsu (jak make run)
egd --profile PATH            # inny profil uruchomienia (domyślnie: config/egida.yaml)

Zmiana polityki

  1. Konsola zmienia każdą sekcję: version, defaults, limits, upstreams, models, agents, budgets i controls. Dla kontroli konsola zmienia kolejność, params detektora i disabled_rules (lista reguł feedu). Zmiana nazwy wpisu aktualizuje odwołania. Konsola nie usuwa wpisu, do którego są odwołania.
  2. Po każdej zmianie konsola sprawdza tekst do zapisu przez parse_policy, czyli walidację proxy (także parametry detektorów). Konsola pokazuje listę problemów. Konsola nie zapisze polityki z problemami.
  3. Przed zapisem (ctrl+s) konsola pokazuje diff. Konsola zapisuje plik atomowo (plik tymczasowy w tym samym katalogu + os.replace), więc poller proxy nigdy nie czyta połowy pliku. Komentarze, kolejność kluczy i styl list zostają (ruamel.yaml).
  4. Jeśli plik zmienił się na dysku po odczycie, konsola pyta: nadpisać plik, wczytać plik z dysku albo anulować.
  5. Działające proxy wczytuje zapisany plik w ok. 1 s. Widok Run porównuje sha256 aktywnej polityki proxy z sha256 pliku.

Uruchomienie proxy

Konsola zapisuje profil uruchomienia config/egida.yaml, gdy zmienisz ustawienie uruchomienia. Bez tego pliku konsola używa wartości domyślnych proxy. Proxy startuje wtedy tak samo jak po make run.

Proxy uruchomione z konsoli działa jako proces potomny konsoli i zapisuje wyjście do var/egida-proxy.log. Konsola zatrzymuje to proxy przy wyjściu. Konsola czyta stan proxy z GET /healthz i GET /api/policy. Konsola oznacza host inny niż loopback, bo endpointy operatora nie mają uwierzytelnienia.

Klucze API agentów

Konsola generuje nowy klucz API, pokazuje go jeden raz i nie zapisuje go. Do polityki trafia tylko sha256 klucza. Agent wysyła klucz w nagłówku Authorization: Bearer <klucz>.

Konsola działa tylko w systemach POSIX (termios: macOS, Linux). Konsola działa natywnie, nie w Docker Compose. make run i edycja YAML w dowolnym edytorze działają jak wcześniej.

Kontrole

Dwadzieścia kontroli działa dziś. Limity, dostęp i budżety to etapy pipeline'u. Kontrole treści to detektory, które włącza polityka. Feed sygnatur to plik reguł z przeładowaniem na żywo. Detektory sprawdzają wszystkie teksty żądania: każdą wiadomość (także system, historię i wyniki narzędzi), argumenty wywołań narzędzi i opisy narzędzi. W tych miejscach jest pośredni prompt injection.

Budżety i pętle

Każdy agent ma budżet tokenów, kosztu i liczby żądań w oknie przesuwnym. Proxy rezerwuje budżet przed modelem i rozlicza go po modelu. Identyczne żądania w krótkim czasie to pętla.

Okno
suma tokenów, kosztu i żądań z ostatnich window_s sekund, per agent
Rezerwacja
najgorszy przypadek: ok. 1 token na 4 znaki wejścia plus całe przycięte max_tokens, koszt z cennika modelu. Przekroczenie blokuje żądanie przed zużyciem zasobów
Rozliczenie
proxy zamienia rezerwację na rzeczywiste usage; przy blokadzie albo błędzie zwalnia rezerwację
Pętla (C16)
odcisk = sha256 kanonicznej postaci (model, wiadomości). Więcej niż max_identical identycznych żądań w identical_window_s → budget.loop
Modele lokalne
też mają cenę w polityce: compute na własnej maszynie to zasób z wymagania R3
Współbieżność
bez locka: reserve nie ma await między odczytem a zapisem, więc w asyncio jest atomowe. Test: 20 równoległych rezerwacji przy limicie 10 → dokładnie 10
Odmowa
HTTP 200 z content_filter, nie 429 (dlaczego)
Ograniczenie
stan jest w jednym procesie i znika przy restarcie; port jest gotowy na Redisa

łańcuch middleware FastAPI (logika związana z HTTP, duplikacja dla MCP); gotowy gateway z wtyczkami (cudza architektura i guardrails, a jury ocenia właśnie te części)
Koszt
więcej plików i interfejsów na starcie; port tylko tam, gdzie są dwie realne implementacje

ADR-0002 · Python 3.12, FastAPI, Pydantic v2, Ollama

Accepted
Decyzja

Odrzucone

Koszt
niższa wydajność proxy; tanie kontrole przed drogimi, pomiar opóźnień per etap

ADR-0003 · Polityka jako wersjonowany kontrakt z hot reloadem

Accepted
Decyzja
YAML z version, schemat Pydantic, źródło za portem PolicySource; walidacja przed atomową podmianą, błędna odrzucona, działa ostatnia poprawna; jedna migawka na żądanie; warianty strict i lenient. Uzupełnienia: brak kontroli w liście = wyłączona (z ostrzeżeniem), polling sha256 co 1 s
Dlaczego
zmiany jury nigdy nie zatrzymują instancji; decyzje są spójne w trakcie przeładowania
Koszt
zmiana schematu wymaga aktualizacji polityk przykładowych; test startu sprawdza każdy plik z config/

ADR-0004 · Semantyka decyzji i jawna obsługa błędów

Accepted
Kontekst
kontrole mogą dać różne wyniki; model bywa wolny albo niedostępny; kod z AI często ukrywa wyjątki, a w warstwie bezpieczeństwa to ciche przepuszczanie ataków
Decyzja
detektor zwraca znaleziska, nie decyduje; najsilniejsza akcja wygrywa; tanie przed drogimi; BLOCK przerywa; każda kontrola ma timeout i on_error (domyślnie block); błąd kontroli to osobne zdarzenie w dzienniku audytu
Koszt
fail-closed przy niedostępnym modelu blokuje ruch; on_error konfigurowalne per kontrola

ADR-0007 · Konsola Egidy: konfiguracja i uruchamianie proxy w terminalu

Accepted

Decyzja

Odrzucone
Textual, prompt_toolkit, urwid (inny wygląd niż pi, większa zależność); pi-tui w TypeScript (drugi runtime i druga kopia schematu); zapis przez PyYAML (usuwa komentarze); endpoint zapisu w proxy (nowa powierzchnia ataku); ustawienia uruchomienia w .env; proxy jako osobny demon
Koszt
jedna zależność więcej; tylko POSIX; własny kod terminala i procesów do utrzymania; profil to drugi plik konfiguracji obok zmiennych środowiskowych

Co już istnieje na rynku

  • LiteLLM, Kong, APISIX, Portkey: dobre w routingu i limitach; kontrole semantyczne tylko w płatnych chmurach albo w wersji Enterprise.
  • agentgateway (Rust, Apache-2.0: LLM + MCP + A2A): najbardziej podobny, ale bez lokalnych kontroli semantycznych i sygnatur ataków.
  • LLM Guard, Rebuff, TensorZero: zarchiwizowane; mcp-scan przeszedł do Snyka. Używamy pomysłów, nie zależności.
  • LiteLLM: audit logs i guardrails per klucz są płatne; rozliczanie kosztów wymaga Postgresa.
