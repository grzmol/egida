AI Control Layer

Lokalne proxy zgodne z API OpenAI. Sprawdza ruch agent ↔ model, redaguje go albo blokuje według jednej polityki edytowanej na żywo. Pilnuje budżetów per agent i zapisuje audyt w łańcuchu hashy.

Zespół froggers · HackYeah 2026, Kraków · zadanie partnerskie Goldman Sachs · stan kodu: main, 3.10.2026. Źródła: docs/architecture.md, docs/adr/, docs/PLAN.md, docs/research/, kod w src/control_layer/.

1. O projekcie

Problem

Zespoły platformowe wpuszczają agentów AI do wrażliwych systemów. Agent wysyła do modelu dane osobowe i sekrety, wykonuje polecenia wstrzyknięte w dokumentach i potrafi wpaść w pętlę, która pali budżet. Zadanie Goldman Sachs: lekka warstwa kontrolna (gateway, proxy, middleware albo SDK), która nadzoruje ruch agentów według jednego centralnego źródła polityk.

Wymagania formalne (R1–R6)

Dwa oficjalne dokumenty podają różne wagi. Przygotowujemy się pod wyższą wagę testów. Jury pracuje bez przygotowania: uruchamia nasze testy, wpisuje własne prompty, zmienia konfigurację na żywo (usuwa kontrole, zmienia progi) i patrzy, czy zmiany działają. Te scenariusze ukształtowały większość decyzji poniżej.

Czym się wyróżniamy

  • Wszystko lokalnie i w open source. Gatewaye (LiteLLM, Kong, Portkey) przekazują kontrole semantyczne do płatnych chmur albo trzymają je w wersjach Enterprise. U nas klasyfikator działa w procesie, bez wywołań do chmury.
  • Jedna polityka, zmiana na żywo. Zła polityka jest odrzucana z powodem, ruch chroni ostatnia poprawna.
  • Każda decyzja ma paragon: id kontroli, wynik, wersja i hash polityki, tagi OWASP/ATLAS, czasy etapów. W odpowiedzi i w audycie.
  • Polski na równi z angielskim: PESEL, NIP, IBAN z sumami kontrolnymi; frazy injection po polsku.
  • Testy, które jury uruchomi samo: te same przypadki działają w CI i przeciw żywej instancji.

Proxy mówi API OpenAI, więc można je postawić za LiteLLM, Kongiem czy agentgateway. Uzupełniamy routing, nie konkurujemy z nim.

2. Szybki start

Wymagania: macOS albo Linux, uv. Do prawdziwych odpowiedzi modelu: Ollama z ollama pull llama3.2:3b. Bez Ollamy proxy działa, a zablokowane żądania dostają odpowiedź; przepuszczone dostaną 502.

uv sync
make run          # proxy na http://127.0.0.1:8080, polityka: config/policy.yaml
make models       # opcjonalnie: Prompt Guard 2 ONNX, potrzebny tylko gdy prompt_guard jest włączony

Podpięcie agenta: zmiana tylko base_url

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="sk-demo-agent")
r = client.chat.completions.with_raw_response.create(
    model="llama3.2:3b", messages=[{"role": "user", "content": "My PESEL is 44051401359"}])
print(r.headers["x-control-decision"], r.parse().choices[0].message.content)  # redact …
curl -s http://127.0.0.1:8080/v1/chat/completions -H 'Authorization: Bearer sk-demo-agent' \
  -d '{"model":"llama3.2:3b","messages":[{"role":"user","content":"Ignore all previous instructions"}]}'
# HTTP 200, finish_reason "content_filter", nagłówek X-Control-Decision: block

3. Architektura

Architektura heksagonalna (porty i adaptery) z liniowym pipeline'em kontroli (ADR-0001). Rdzeń zawiera całą logikę decyzji i nie wie nic o HTTP, plikach, Ollamie ani modelach. Świat zewnętrzny wchodzi wyłącznie przez porty, czyli interfejsy typing.Protocol z core/ports.py.

4. Przepływ żądania

Pipeline ma stałą kolejność. Każde żądanie używa jednej migawki polityki od początku do końca, więc przeładowanie w trakcie nie daje decyzji z dwóch różnych polityk.

Czerwona ramka: etap, który może zablokować. Pierwsza blokada kończy pipeline; model nie jest wywoływany, a rezerwacja budżetu jest zwalniana.

Kroki szczegółowo

  1. Wejście HTTP. http_api.py liczy sha256 klucza z nagłówka Authorization i szuka agenta w polityce. Brak lub nieznany klucz daje 401. Treść żądania mapuje na Interaction: wiadomości (także system, historia, role: tool), wywołania narzędzi i ich opisy.
  2. Limity (C17). Za długie wejście lub za dużo wiadomości daje blokadę. Żądane max_tokens jest przycinane do limitu z polityki, więc agent nie może zamówić dowolnie długiej odpowiedzi.
  3. Dostęp do modelu (C02). Model spoza allowed_models agenta daje blokadę access.model.
  4. Rezerwacja budżetu (C15/C16). Szacunek tokenów i kosztu jest rezerwowany przed wywołaniem modelu. Odmowa daje blokadę budget.tokens, budget.cost, budget.requests albo budget.loop.
  5. Kontrole wejścia. Detektory po stronie input w kolejności z polityki (tanie najpierw), każdy z własnym timeoutem. Redakcje z wielu detektorów są łączone i stosowane, zanim tekst trafi do modelu.
  6. Model. Wywołanie upstreamu z polityki (upstreams). Błąd sieci lub HTTP daje 502 i zdarzenie upstream_error.
  7. Kontrole wyjścia. Te same detektory po stronie output sprawdzają odpowiedź, np. czy model nie zwrócił PESEL-u lub klucza.
  8. Rozliczenie. Rezerwacja jest zamieniana na rzeczywiste zużycie z usage upstreamu.
  9. Agregacja i audyt. Najostrzejsza akcja wygrywa. Powstaje jedno zdarzenie audytu z wynikami, budżetem i czasami etapów.

Czasy etapów trafiają do audytu pod kluczami limits, access, budget, input:<kontrola>, redact_input, model, output:<kontrola>, total. Z nich dashboard liczy p50 i p95.

Streaming

stream: true omijałby kontrole wyjścia, gdyby tokeny szły do klienta na bieżąco. Proxy pobiera więc całą odpowiedź, sprawdza ją, a potem odtwarza jako SSE zakończone [DONE]. Klient działa bez zmian; tracimy tylko strumieniowanie token po tokenie.

5. Semantyka decyzji

Źródło: ADR-0004 i ADR-0005.

  • Trzy akcje: ALLOW, REDACT, BLOCK. Najostrzejsza wygrywa: BLOCK > REDACT > ALLOW.
  • Pierwsza blokada przerywa pipeline. Model nie jest wywoływany, dalsze kontrole się nie uruchamiają.
  • Próg. Znalezisko z wynikiem poniżej threshold kontroli jest zapisywane w audycie z akcją ALLOW. Widać je, ale nie blokuje.
  • REDACT bez spanów zamienia się w BLOCK. Czego nie da się zlokalizować, tego nie da się zamaskować; przepuszczenie byłoby wyciekiem.
  • Błąd kontroli. Wyjątek albo przekroczenie timeout_ms daje zdarzenie control_error. Decyduje on_error kontroli: domyślnie block (fail-closed). Błąd nigdy nie znika po cichu.
  • Detektor bez zasobów. Jeśli fabryka detektora przy starcie rzuca OSError (np. brak plików modelu), aplikacja i tak startuje. Detektor zastępuje atrapa, która przy każdym wywołaniu zgłasza błąd, więc włączona kontrola działa według swojego on_error. Świeży klon startuje bez 300 MB modeli, a włączona kontrola bez modelu nie przepuszcza ruchu.
  • Audyt nie zawiera treści promptów ani odpowiedzi. Tylko zamaskowane dowody (np. pesel 44*******59).

Odpowiedź blokująca

Zablokowane żądanie dostaje HTTP 200 z poprawnym obiektem chat.completion, finish_reason: "content_filter", nagłówkami X-Control-* i polem control_layer. Prawdziwa odpowiedź z bieżącego kodu:

Kody HTTP

KodKiedy
200każda decyzja: allow, redact i block (blok z content_filter)

400niepoprawne wejście (zły JSON, brak wymaganych pól)

Dlaczego 200, a nie 403 czy 429? Narzędzia red-teamingowe (garak, promptfoo) i SDK liczą kody błędów jako awarię, nie jako skuteczną obronę, a agent nie dostaje czytelnej odpowiedzi. SDK OpenAI automatycznie ponawia 429, więc odmowa budżetu jako 429 sama tworzyłaby pętlę, którą budżet ma zatrzymywać. Ten sam mechanizm stosują dostawcy modeli: finish_reason: "content_filter".

6. Polityka

Jeden plik YAML (config/policy.yaml) steruje wszystkim: kontrolami, progami, akcjami, modelami, agentami i budżetami. Schemat to Pydantic v2 w core/policy.py z extra="forbid": literówka w nazwie pola odrzuca całą polityką, zamiast zostać po cichu zignorowana. Parametry każdego detektora są walidowane przy ładowaniu polityki jego własnym modelem Params, a nie dopiero przy pierwszym żądaniu.

Przeładowanie na żywo

  1. PolicyFile co 1 s liczy sha256 pliku (polling, nie obserwator systemu plików: działa tak samo na macOS, Linuksie, w Dockerze i przy zapisie przez edytory, które podmieniają plik).
  2. Zmiana hasha: parsowanie (yaml.safe_load), walidacja schematu i parametrów detektorów.
  3. Poprawna: atomowa podmiana niezmiennej migawki i zdarzenie policy_reloaded z diffem w audycie.
  4. Niepoprawna: odrzucona, zdarzenie policy_rejected z powodem, GET /api/policy pokazuje last_error, dashboard pokazuje czerwony baner „Policy change REJECTED”. Ruch dalej chroni ostatnia poprawna polityka.
  5. Usunięcie lub wyłączenie kontroli jest dozwolone, ale widoczne: dashboard pokazuje żółty baner „Posture weakened” z nazwami kontroli.

Każde żądanie bierze jedną migawkę na starcie, więc przeładowanie w połowie żądania go nie dotyczy. W nagłówku X-Policy-Sha256 i w audycie widać, która wersja pliku podjęła decyzję.

Detektory skanują wszystkie teksty żądania: każdą wiadomość (także system, historię i wyniki narzędzi role: tool), argumenty wywołań narzędzi i tools[].description. Atak schowany w wyniku narzędzia albo w opisie narzędzia MCP to typowa droga pośredniego prompt injection.

PII (C04) — detectors/pii.py

  • Typy: email, phone, pesel, nip, iban, card.
  • Numery są uznawane tylko z poprawną sumą kontrolną (PESEL, NIP, IBAN mod 97, karta wg Luhna; biblioteka python-stdnum). Numer zamówienia czy faktury, który wygląda jak PESEL, przechodzi. To główna obrona przed fałszywymi alarmami.
  • Spany liczone na oryginalnym tekście, więc redakcja zastępuje dokładnie wykryty fragment znacznikiem [REDACTED:pesel].
  • Parametry: entities (podzbiór typów), extra_patterns (własne regexy; walidowane przy ładowaniu: poprawność, brak dopasowania pustego ciągu, brak kolizji z typami wbudowanymi).
  • Tagi: owasp.llm02-2025, atlas.AML.T0057.

Sekrety (C05) — detectors/secrets.py

  • Reguły przepisane ręcznie na wzór gitleaks.toml (MIT): aws_access_key, aws_secret_key, github_token, gitlab_token, private_key, jwt, slack_token, conn_string, openai_key, stripe_key, google_api_key, npm_token, sendgrid_key, bearer_token, keyed_secret.
  • high_entropy: tokeny o entropii Shannona powyżej progu (domyślnie 4.5, min. 32 znaki). Mają wynik 0.6, poniżej domyślnego progu 0.8, więc trafiają do audytu bez blokowania. Polityka strict obniża próg i je blokuje.
  • Parametry: rules, entropy_threshold, entropy_min_len.
  • Tagi: owasp.llm02-2025, asi.asi03, atlas.AML.T0055.

Heurystyki injection (C06) — detectors/injection_heuristics.py, normalize.py

Wzorce działają na widokach tekstu z normalize.views(), nie na surowym tekście:

  • normalizacja: NFKC, małe litery, usunięte znaki niewidoczne (zero-width, wszystkie znaki kategorii Cf), usunięte znaki łączące, polskie znaki bez ogonków, łacińskie odpowiedniki homoglifów (cyrylica, greka, małe kapitaliki, litery w kwadratach i kółkach typu 🅰);
  • dodatkowe widoki: zdekodowane segmenty base64 i ROT13.

Wzorce (22): ignore_instructions, ignore_everything_before, reveal_system_prompt, ask_system_prompt, repeat_above, persona_override, you_are_dan, no_restrictions, forget_rules, obey_only_me, ignore_authority, policy_revoked, do_anything_now, mode_switch, fake_role_header i polskie pl_ignore_instructions, pl_ignore_instructions_after, pl_reveal_system_prompt, pl_reveal_own_instructions, pl_persona_override, pl_no_restrictions, pl_disobey.

Wzorce są celowo wąskie. Pułapki fałszywych alarmów muszą przechodzić, np. „Ignore the typos in my previous message”. Słowa mieszające alfabet łaciński i cyrylicę dostają wynik 0.6: poniżej domyślnego progu, ale strict je blokuje. Parametry: extra_patterns, disabled_patterns. Tagi: owasp.llm01-2025, asi.asi01, atlas.AML.T0051.

Prompt Guard (C07) — detectors/prompt_guard.py

  • Llama Prompt Guard 2 86M (klasyfikator BENIGN/MALICIOUS) w ONNX, w procesie przez onnxruntime i tokenizers, bez torcha. Ok. 110 ms na CPU (pomiar z research 02).
  • Dwa przebiegi na tekst: okna o rozmiarze kontekstu modelu (510 tokenów treści, krok 446) i pojedyncze zdania. Bez drugiego przebiegu jedno zdanie ataku w długim dokumencie dostaje ok. 0.01 i ginie.
  • Powtórzone teksty są cache'owane; praca CPU idzie w wątku (anyio).
  • Parametry: max_windows (16), roles (system, user, tool), scan_tool_descriptions. Tylko strona wejścia.
  • Model pobiera make models z przypiętą rewizją i sha256. Bez plików kontrola działa jak fail-closed (patrz §5).
  • Licencja Llama 4 Community: wymagany napis Built with Llama.

8. Budżety i pętle

adapters/budget_memory.py (InMemoryBudgetStore) implementuje port BudgetStore: reserve, settle, release, usage.

  • Okno przesuwne per agent (window_s): suma tokenów, kosztu i liczby żądań z ostatniego okna.
  • Rezerwacja przed modelem: najgorszy przypadek, czyli ok. 1 token na 4 znaki wejścia plus całe przycięte max_tokens, i koszt z cennika modelu. Jeśli rezerwacja przekroczyłaby limit, żądanie jest blokowane, zanim zużyje cokolwiek.
  • Rozliczenie po modelu: rezerwacja jest zastępowana rzeczywistym usage. Przy blokadzie lub błędzie rezerwacja jest zwalniana.
  • Pętla agenta (C16): odcisk żądania to sha256 kanonicznej postaci (model, wiadomości). Więcej niż max_identical identycznych żądań w identical_window_s daje budget.loop.
  • Koszt modeli lokalnych też jest liczony (cena w polityce), bo compute na lokalnej maszynie to też zasób, którego dotyczy wymaganie R3.
  • Bez locka. reserve nie ma żadnego await między odczytem a zapisem, więc w pętli asyncio jest atomowe. Test: 20 równoległych rezerwacji przy limicie 10 daje dokładnie 10 przyjętych.
  • Odmowa budżetu to HTTP 200 z content_filter, nie 429 (powód w §5).
  • Stan żyje w jednym procesie i znika przy restarcie. Port pozwala podmienić go na Redisa bez zmian w rdzeniu.

Łańcuch hashy

Każdy wpis ma seq, prev_hash (hash poprzedniego wpisu; pierwszy ma same zera) i hash = sha256 kanonicznego JSON-a wpisu. Zmiana, usunięcie lub wstawienie wpisu w środku psuje łańcuch od tego miejsca. make verify-audit (python -m control_layer.adapters.audit_jsonl verify var/audit.jsonl) wypisuje OK n events albo numer pierwszego złego wpisu. Plik jest tylko dopisywany; po restarcie łańcuch jest kontynuowany od ostatniego wpisu.

Łańcuch nie chroni przed kimś, kto przepisze cały plik od nowa (wtedy potrzebny jest zewnętrzny zapis ostatniego hasha). Wykrywa natomiast każdą częściową edycję, a tego dotyczy typowy scenariusz zacierania śladów.

11. Decyzje (ADR)

Pełne teksty: docs/adr/. Każda decyzja o bibliotece, modelu, formacie danych, protokole lub zmianie portów wymaga ADR przed implementacją.

ADR-0001: Architektura heksagonalna z liniowym pipeline'em

Kontekst. Kontrole deterministyczne i semantyczne, budżety, audyt; jury ocenia architekturę (20%) i zmienia konfigurację na żywo. Projekt ma rosnąć o kolejne kontrole i protokoły (MCP, agent ↔ agent). Kod powstaje z pomocą AI, która bez twardych granic miesza logikę z frameworkiem.

Decyzja. Rdzeń core/ bez frameworków; świat przez porty; stała kolejność etapów; kontrole jako Detector; adaptery tylko w app.py; granice pilnowane przez import-linter.

Odrzucone. Łańcuch middleware FastAPI: szybki start, ale logika związana z HTTP, a MCP i agent ↔ agent wymagałyby duplikacji. Gotowy gateway z wtyczkami: architektura i guardrails byłyby cudze, a to one są oceniane; ryzyko licencyjne.

Koszt. Więcej plików i interfejsów na starcie. Mitygacja: port tylko tam, gdzie są dwie realne implementacje.

ADR-0002: Python 3.12, FastAPI, Pydantic v2, Ollama

Decyzja. Python 3.12 (modelscan wymaga <3.13), uv i lockfile, FastAPI + uvicorn, Pydantic v2, httpx, pytest, ruff, mypy, import-linter. Ollama jako natywny proces obok (Metal na Macu), modele ONNX w procesie proxy.

Odrzucone. Go: szybsze proxy, słabszy ekosystem ML/NLP i wolniejsze pisanie testów danych. Rust: najlepsza wydajność, najwolniejsza iteracja w 24 h. TypeScript: dobre wsparcie AI, słabsze biblioteki do analizy treści.

Koszt. Niższa wydajność proxy. Mitygacja: tanie kontrole przed drogimi, pomiar opóźnień per etap, porty pozwalają przepisać gorące ścieżki.

ADR-0003: Polityka jako wersjonowany kontrakt z hot reloadem

Decyzja. YAML z polem version; schemat Pydantic; źródło za portem PolicySource; walidacja przed podmianą, atomowa zamiana niezmiennego obiektu, błędna polityka odrzucona, działa ostatnia poprawna; jedna migawka na żądanie; warianty strict i lenient. Uzupełnienia z research (Z-8): brak kontroli w liście = kontrola wyłączona, z ostrzeżeniem „posture weakened”; przeładowanie przez polling sha256 co 1 s.

Dlaczego. Zmiany jury nigdy nie wywracają instancji, a decyzje są spójne w trakcie przeładowania. Koszt: zmiana schematu wymaga aktualizacji przykładowych polityk, co pilnuje test startu na każdym pliku z config/.

ADR-0004: Semantyka decyzji i jawna obsługa błędów

Kontekst. Kontrole mogą się nie zgadzać, model lokalny bywa wolny lub niedostępny, jury atakuje ad hoc (30% oceny). Kod z AI często połyka wyjątki, a w warstwie bezpieczeństwa to ciche przepuszczanie ataków.

Decyzja. Detektor zwraca znaleziska albo nic, nie decyduje. Najostrzejsza akcja wygrywa; redakcje są łączone. Tanie przed drogimi; BLOCK przerywa pipeline. Każda kontrola ma timeout i on_error, domyślnie block. Błąd kontroli to osobne zdarzenie audytu.

Koszt. Fail-closed przy niedostępnym modelu blokuje ruch. Mitygacja: on_error konfigurowalne per kontrola (lenient ustawia allow dla Prompt Guarda).

ADR-0005: Zależności, modele i kontrakt odpowiedzi blokady v1

Decyzja. Jeden zbiorczy ADR zamiast osobnego na każdą bibliotekę (czas do draftu). Lista zależności runtime zamknięta (§15). Model: Prompt Guard 2 86M ONNX z przypiętą rewizją. Blokada jako HTTP 200 z content_filter; bez 429 dla budżetów. Detektor bez zasobów zastępowany atrapą fail-closed.

Odrzucone. Blokada jako 403/422. Brak startu bez modeli (świeży klon i CI nie działałyby bez 300 MB modeli, choć kontrola jest wyłączona). detect-secrets, Presidio, cennik LiteLLM.
